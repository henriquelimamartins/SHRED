# Tests

Automated tests for The Shred Roadmap (Phase 1 · Safety net). They are not part of the app.

- Runner: Playwright (`@playwright/test` 1.63.0), Chromium, two projects: `desktop` (1440×900) and `mobile` (Pixel 7).
- The app is served locally by `tests/support/static-server.js`.
- Firebase is never contacted: the three Firebase SDK files are replaced by stand-ins in
  `tests/support/firebase-stubs/`, and every other external request is blocked (`tests/support/app.js`).
  Web fonts are blocked too, so screenshots use fallback fonts.
- The Firestore stand-in can hold or fail `getDoc` when a test sets `window.__SHRED_TEST_FLAGS__` (`holdGetDoc`, `failGetDoc`) before the app starts (Phase 3.3).
- Since Phase 3.4 the Firestore stand-in also has `runTransaction` (the app's only way to write to the cloud); it can fail (`failTransaction`, as when offline) or hold each transaction until the test calls `window.__SHRED_TEST_RELEASE_TRANSACTION__()` (`holdTransaction`). Another device saving is simulated by changing `window.__SHRED_TEST__.docs` directly.
- The clock is fixed at 2026-11-10 12:00 UTC (a Tuesday) so dates are predictable (`DEFAULT_NOW` in `tests/support/app.js`).
  `daily.spec.js`, `improv.spec.js`, `streak.spec.js` and `local-day.spec.js` also fix the browser time zone to `Europe/Lisbon` (the owner's) and moves the clock where a test needs another day.
- Test data shaped like the app's saved state lives in `tests/support/fixtures.js`. The fixtures have no `schemaVersion` on purpose: they are data as saved before Phase 3 (version 0), so every test also exercises the 0 → 1 migration.
- Tests named `current behaviour: …` document known risks on purpose (D81, D83) and other problems found on `main`. The Phase 3 fixes update them in the same PR.
- Run: `npm install` then `npm test`. Screenshots and traces go to `test-results/` (not committed).
- On GitHub: the `Tests` workflow (`.github/workflows/tests.yml`) runs the whole suite on every pull request to `main` and can be started by hand from the Actions tab. It only reads the code, uses no secrets, and keeps the report for 14 days when a test fails.

| `stale-sessions.spec.js` | Phase 3.4 (D105): every cloud write is a transaction numbered by `syncRev` (+1 each time, kept on the device too); a stale session (another device saved since it read) never overwrites the newer copy (automatic save, manual Save, Reset): the cloud wins, the local change is in a backup and a message says so; saves made during a write merge into one follow-up write; when the app becomes visible again or the network returns a newer copy is loaded; offline changes are marked pending and sent later only if the cloud has not moved on (also at the next start-up); a pending mark for another account is never used; data from a newer app version (`schemaVersion`) is never written over. |
| `reset.spec.js` | Phase 3.5 (D83, D106): the confirmation says what is erased and kept; Reset erases Technique, every mark in `checks` (Technique, BHGS theory videos, Creative), Improv and legacy DOJO data, and keeps streak, calendar, today's DAILY session, SETUP, unknown fields, `schemaVersion` and the DOJO sound setting; the backup holds what was erased; no migration backup after a reload; signed in it is refused until the cloud was read, then sent as a checked write (`syncRev` + 1), and while offline it stays pending and is sent when the network returns. |
